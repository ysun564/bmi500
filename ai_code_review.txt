4. Issues Found
---------------
Overall assessment: the implementation is correct for valid input. It meets
the assignment requirements (dot_product uses a for loop,
matrix_vector_product uses dot_product, main uses random 1000 x 1000 data).
It also rejects every failure mode listed in the assignment. The issues below
are about performance, error-message quality, consistency, and test gaps.
They are ordered from most to least important.

Issue 1 - Validation dominates runtime; the vector is re-validated per row
  Severity: Medium (performance)
  Location: lines 54 and 58, together with lines 22-23 and 13-17
  Details: matrix_vector_product validates `vector` on line 54, then calls
    dot_product once per row. Each call validates both the row and the vector
    again. For a 1000 x 1000 input that is 2001 _validate_vector calls and
    2,001,000 element checks, and 1,000,000 of those re-check the same vector.
    Each element also needs up to three isinstance calls, and the
    `isinstance(value, Number)` check goes through the slow ABC
    __instancecheck__ path because float and int are only registered with
    numbers.Number. Measured: 0.605 s with validation vs 0.043 s without,
    so about 93% of the runtime is validation, not multiplication.
  Suggestion: validate the vector once and each row once inside
    matrix_vector_product. Then multiply through an internal unchecked helper
    (for example `_dot_unchecked`), and keep the public dot_product fully
    validated. Add a fast path such as `if type(value) in (int, float):
    continue` before the ABC check. A prototype of this approach ran in
    0.073 s (about 8x faster) and gave identical results.

Issue 2 - Error messages name the wrong argument for matrix rows
  Severity: Medium (usability / debuggability)
  Location: line 58 (rows are passed to dot_product as "vector_a")
  Details: invalid values inside the matrix are reported as problems with
    "vector_a", a name the caller of matrix_vector_product never used, and
    the message does not say which row failed:
      matrix_vector_product([[1, "two"]], [3, 4])
        -> TypeError: vector_a values must be numeric
      matrix_vector_product([[[1], [2]]], [1, 2])
        -> ValueError: vector_a must be one-dimensional
    For a 1000-row matrix, the user cannot tell where the bad value is.
  Suggestion: validate rows in matrix_vector_product with a descriptive name,
    for example `_validate_vector(row, f"matrix row {i}")`. Include actual
    sizes in dimension errors, for example
    "matrix has 3 columns but vector has length 2".

Issue 3 - Inconsistent exception types and dimension detection
  Severity: Low-Medium (API consistency)
  Location: lines 8-9, 14-17, 40-41, 45-47
  Details:
    - A matrix/vector that is not a list or tuple raises TypeError (lines 9,
      41), but a row that is not a list or tuple raises ValueError (line 47).
      A NumPy array, str, or dict row therefore gets
      "ValueError: matrix must be two-dimensional", even though it is really
      a type problem.
    - Dimension detection only recognizes list/tuple. A nested NumPy array or
      set inside a vector is reported as "values must be numeric" (TypeError)
      instead of "must be one-dimensional" (ValueError). So the same kind of
      mistake raises different exceptions depending on the container type.
    - Only list/tuple are accepted at all. NumPy arrays, array.array, ranges,
      and generators are rejected, and the docstrings do not say so.
  Suggestion: pick one convention (for example TypeError for wrong container
    or element types, ValueError for wrong shapes or sizes), apply it
    everywhere, and document the accepted input types in the docstrings. If
    the exception type on line 47 is changed, test
    test_rejects_non_two_dimensional_matrix must be updated to match.

Issue 4 - numbers.Number accepts values the arithmetic cannot handle safely
  Severity: Low-Medium (robustness)
  Location: line 16
  Details:
    - decimal.Decimal passes validation, but mixing it with float fails in
      the multiplication loop with a raw Python error
      ("unsupported operand type(s) for *: 'decimal.Decimal' and 'float'")
      instead of the function's own validation message.
    - complex values are accepted. The product is computed without
      conjugation, which is correct for A @ v but not the Hermitian inner
      product some users expect from a function named dot_product. This is
      not documented.
    - NaN and +/-inf are accepted silently. Overflow (1e200 * 1e200) and
      inf * 0 quietly produce nan.
  Suggestion: restrict elements to numbers.Real (still excluding bool) unless
    complex/Decimal support is intended. Consider rejecting non-finite values
    with math.isfinite, or document that they propagate.

Issue 5 - Misleading / misplaced comments
  Severity: Low (maintainability)
  Location: lines 4-5, 36-37, 53, 62-63
  Details:
    - Line 53 says "dot_product validates that each row and the vector
      contain numbers." The next line validates the vector explicitly anyway,
      and that duplication is the cause of Issue 1. The comment no longer
      describes why the code is written this way.
    - The scaffold comments on lines 4-5 ("create a function to compute the
      dot product ...") sit above _validate_vector, not above dot_product, so
      they describe the wrong function.
    - The instruction comments ("add comments for the selected function") are
      assignment prompts, not code documentation.
  Suggestion: move or remove the scaffold comments if the assignment allows
    it, and rewrite line 53 to match the actual validation strategy.

Issue 6 - Edge-case messages that point at the wrong cause
  Severity: Low (usability)
  Location: lines 49-56
  Details:
    - matrix_vector_product([[]], [1]) reports "matrix columns must equal the
      vector length" instead of saying the matrix rows are empty.
    - When both inputs are invalid, the vector is checked before the matrix
      contents, so matrix_vector_product([[1, "x"]], []) reports only
      "vector must not be empty".
    - Row-length mismatch ("matrix rows must have the same length") does not
      name the offending row or its length.
  Suggestion: check the matrix fully (including empty rows) before the vector,
    and include row indices and lengths in messages.

Issue 7 - main() is not reproducible and does not validate `size`
  Severity: Low
  Location: lines 64-71
  Details:
    - The random generator is not seeded, so runs cannot be reproduced.
    - `size` is not validated: size=0 or size=-3 fail inside
      matrix_vector_product with "matrix must not be empty", and size=2.5
      fails with a raw range() TypeError.
    - The function is described as a test, but it only prints the output
      length. It does not check the result or report timing.
  Suggestion: accept an optional `seed` argument (or a random.Random
    instance), validate that `size` is a positive int, and optionally print
    the elapsed time or compare against a reference result.

Issue 8 - Non-idiomatic loop and uncompensated floating-point summation
  Severity: Low (style / numerical accuracy)
  Location: lines 29-31
  Details: `for index in range(len(vector_a))` with indexing is less idiomatic
    and slightly slower than `for a, b in zip(vector_a, vector_b)`. Plain
    accumulation with += loses precision under cancellation:
    dot_product([1e16, 1.0, -1e16], [1.0, 1.0, 1.0]) returns 0.0, while
    math.fsum gives the exact 1.0.
  Suggestion: iterate with zip, which still satisfies the "use a for loop"
    requirement. If accuracy matters more than matching NumPy, accumulate
    with math.fsum. Otherwise document the limitation; NumPy does not
    compensate either.

Issue 9 - Test coverage gaps in matvec_tests.py
  Severity: Low (test quality)
  Details:
    - Lines 9 and 41 (TypeError for a vector/matrix that is not a list or
      tuple) are never executed by the tests.
    - Rejection of bool values (`isinstance(value, bool)` on line 16) is never
      exercised. Tests only use "two"/"four", which fail the Number check
      first.
    - No tests use tuple inputs, float values (with assertAlmostEqual), a
      1 x 1 matrix, a non-square matrix, or complex/Decimal/NaN inputs.
    - No randomized test compares against a reference implementation (for
      example NumPy's `@`, or a small hand-written triple loop).
    - The only error-message checks use short regexes ("numeric",
      "same length"), so Issue 2 (wrong argument name) is not caught.
  Suggestion: add the tests above, especially a TypeError test for
    non-list/tuple inputs, a bool-rejection test, and a randomized
    comparison test.
